# The cross-region-backup example

`examples/cross-region-backup` keeps a copy of the data in a second region, and its README walks
through a restore there.

## What it deploys

In the primary region, in an existing VPC with a NAT gateway you already have:

- **One engine** on ECS Fargate, 1 vCPU and 2 GiB, and the migrate task definition.
- **PostgreSQL on RDS**, `db.t4g.medium`, Multi-AZ, deletion protection on, 14 days of automated
  backups.
- **A network load balancer**, internal, with one MLLP listener, the KMS key, the database's secret,
  the log groups, the security groups and the roles.
- **The channel** in `project/`: ADT over MLLP in, admissions over MLLP out to the lab.

In the backup region, `us-west-2` here:

- **A replication of the automated backups**, kept 14 days, so you can restore to any point in that
  window there. The module's output `database_instance_arn` names the database it copies.
- **A KMS key**, rotated yearly, that encrypts the replicated backups and any instance restored from
  them.

## The restore

Once the primary engine is stopped, or its region is gone: restore with
`aws rds restore-db-instance-to-point-in-time --source-db-instance-automated-backups-arn` into a new,
private, encrypted instance with `rds.force_ssl` on; give it a new master password and store its URL
in a secret in the backup region; then deploy the module there on that database, as
[existing-database](./example-existing-database.md) does, with the image and the master key's
secret replicated to that region beforehand. The example's README has every command.

## When to choose it

When your data must survive the loss of a region, and a restore by hand is an answer you can accept.

## What it does not cover

- Automatic promotion to the second region: see
  [second-region-disaster-recovery](./example-second-region-disaster-recovery.md), which waits on the
  engine.
- Messages the engine acknowledged after the restore point.
- The image, the master key's secret and a network in the backup region, which you replicate and
  build beforehand.

## What it costs to leave running

We give what bills, not prices: AWS sets those per region and changes them. Price each line in the
[AWS Pricing Calculator](https://calculator.aws/) for your region.

| What | How it bills while it runs |
| --- | --- |
| The engine, Fargate, 1 vCPU and 2 GiB | per second the task runs, all month |
| The database, `db.t4g.medium`, Multi-AZ | per hour of the instance, twice over for the standby, all month |
| Database storage, 50 GiB to start | per GB-month allocated, twice over with Multi-AZ, and backups beyond the database's size |
| The network load balancer | per hour it exists, and per capacity unit used |
| The KMS key and the database's secret | per month each, and per request or call |
| CloudWatch Logs | per GB ingested, and per GB-month kept for `log_retention_days` (365) |
| Your NAT gateway, already there | per GB the tasks send through it |
| The replicated backups | per GB-month stored in the backup region, for the snapshots and the transaction logs of 14 days |
| Data transfer between regions | per GB copied |
| The backup region's KMS key | per month, and per request |

Nothing runs in the backup region until you restore; a restore then bills for what you deploy there.

### README.md

````md title="examples/cross-region-backup/README.md"
# cross-region-backup

One engine in the primary region, with the database's automated backups replicated to a second
region, and a restore there written out step by step.

## What it builds

In the primary region, in an existing VPC with a NAT gateway you already have:

- one engine on ECS Fargate, 1 vCPU and 2 GiB, and the migrate task definition;
- PostgreSQL on RDS, Multi-AZ, `db.t4g.medium`, deletion protection on, with 14 days of automated
  backups (`backup_retention_days`);
- an internal network load balancer with one MLLP listener, the KMS key, the secret, the log groups,
  the security groups and the roles;
- the one channel in [`project/`](project): ADT over MLLP in, admissions over MLLP out to the lab.

In the backup region (`backup_region`, `us-west-2` here):

- a replication of the database's automated backups
  (`aws_db_instance_automated_backups_replication`), kept for the same 14 days, so you can restore
  to any point in that window there;
- a KMS key, rotated yearly, with the alias `alias/pathways-backup-database`, which encrypts the
  replicated backups and any instance you restore from them.

Nothing runs in the backup region until you restore.

## When to choose it

When your data must survive the loss of a region, and a restore that takes you an hour or more is
an answer you can accept. It is the cheapest step towards disaster recovery: a copy of the data,
with no second engine and no second database running.

## What it costs

We give what bills, not prices: AWS sets those per region and changes them.

- Everything in the primary region, as in [`production`](../production) at the module's default
  sizes: Fargate, the database twice over for Multi-AZ, the network load balancer, the key, the
  secret, the logs and your NAT gateway.
- The replicated backups: storage per GB-month in the backup region, for the snapshots and the
  transaction logs of the retention window.
- Data transfer between regions, per GB, for each snapshot and log copied.
- The backup region's KMS key, per month and per request.
- A restore, while it runs: the instance, its storage and everything you deploy beside it.

## What it does not cover

- **Automatic promotion.** A standing engine in the second region that takes over when the first
  region fails is a different shape, and waits on the engine: see
  [`second-region-disaster-recovery`](../second-region-disaster-recovery). Here a person decides to
  restore and does it.
- **Messages after the restore point.** A restore brings back the database as it was at the time you
  choose, at most the latest restorable time RDS reports (usually a few minutes behind). Messages
  the engine accepted and acknowledged after that are not in it. Your senders will not resend what
  was acknowledged: reconcile with them.
- **The image and the master key in the backup region.** Replicate both before you need them: the
  image with ECR replication, and the master key's secret with Secrets Manager replication. A restored
  database is unreadable without the master key.
- **A network in the backup region**: a VPC, subnets in two zones, and the routes your senders and
  destinations need.

## Restore in the backup region

Do this only once the primary engine is stopped, or its region is gone: two engines on two copies of
the data both deliver, and a destination gets each message twice. Every name below is an example.

1. Find the latest point you can restore to, in the backup region:

   ```sh
   aws rds describe-db-instance-automated-backups --region us-west-2 \
     --query 'DBInstanceAutomatedBackups[?DBInstanceIdentifier==`pathways-backup`].[DBInstanceAutomatedBackupsArn,RestoreWindow.LatestTime]'
   ```

   The first value is also this example's output `replicated_backups_arn`.

2. Create, in the backup region, a DB subnet group in two availability zones, a security group for
   the database, and a parameter group of the same family (`postgres17`) with `rds.force_ssl` set to
   1, so the restored database refuses connections without TLS, as the module's does.

3. Restore into a new instance, encrypted, private and Multi-AZ:

   ```sh
   aws rds restore-db-instance-to-point-in-time --region us-west-2 \
     --source-db-instance-automated-backups-arn "$REPLICATED_BACKUPS_ARN" \
     --target-db-instance-identifier pathways-restored \
     --use-latest-restorable-time \
     --db-subnet-group-name pathways-restored \
     --vpc-security-group-ids "$DATABASE_SECURITY_GROUP_ID" \
     --db-parameter-group-name pathways-restored \
     --no-publicly-accessible --multi-az --deletion-protection
   aws rds wait db-instance-available --region us-west-2 --db-instance-identifier pathways-restored
   ```

   Use `--restore-time` instead of `--use-latest-restorable-time` to pick an earlier point.

4. Give it a new master password, since the old one is in the primary region's secret, and store the
   connection URL in a secret in the backup region. Read the password from a file or a prompt, never
   from the command line's history:

   ```sh
   aws rds modify-db-instance --region us-west-2 --db-instance-identifier pathways-restored \
     --master-user-password "$NEW_PASSWORD" --apply-immediately
   aws secretsmanager create-secret --region us-west-2 --name pathways-restored/database-url \
     --secret-string "postgres://pathways:${NEW_PASSWORD}@<restored address>:5432/pathways"
   ```

5. Deploy the module in the backup region on that database: the
   [`existing-database`](../existing-database) example, with `database_url_secret_arn` the new
   secret, `database_security_group_id` the database's group from step 2, the replicated master key
   secret and image, and the same `mllp_sources`. Run its migrate task before the engine, as for any
   deploy.

6. Point your senders at the new load balancer, through the DNS name they use, and check the engine
   reports ready. The old engine's engine lease in the restored database has long expired, so the new
   engine takes it.

When the primary region is back, do not start the old engine against its old database: that copy is
behind the restored one. Rebuild the primary from a backup of the restored database, or keep
running in the backup region.

## Use it

Every value in [`variables.tf`](variables.tf) is a placeholder. Copy `project/` into a project
`pathways init` made, add the RDS global bundle, the MLLP source's certificate and key and the lab's
CA under `certs/`, build the image and push it, set the variables, then plan and apply from your own
pipeline with your own credentials. Practise the restore before you need it. CI here validates this
directory and tests it against mocked providers (`tests/example-cross-region-backup`); nothing in this
repository applies it.
````

### main.tf

```hcl title="examples/cross-region-backup/main.tf"
# One engine in the primary region, with the database's automated backups replicated to a second
# region, so the data survives the loss of the first. RDS copies each snapshot and the transaction
# logs to the backup region and keeps them there for backup_retention_days, encrypted under a key
# that lives in that region. Nothing runs in the backup region until you restore: the README walks
# through the restore, by hand, into a new instance there.
#
# Promotion is not here: a standing engine in the second region that takes over on its own waits on
# the engine. See ../second-region-disaster-recovery.
#
# Every value here is a placeholder: the VPC and subnet ids, the account id 123456789012, the image
# digest and the secret ARN. Put your own in before you plan.

provider "aws" {
  region = var.region

  default_tags {
    tags = {
      Project = "pathways-backup"
    }
  }
}

# The backup region: the replicated backups and their key are created there.
provider "aws" {
  alias  = "backup"
  region = var.backup_region

  default_tags {
    tags = {
      Project = "pathways-backup"
    }
  }
}

module "pathways" {
  source = "../.."

  name   = "backup"
  vpc_id = var.vpc_id

  private_subnet_ids  = var.private_subnet_ids
  allowed_cidr_blocks = var.allowed_cidr_blocks

  image = var.image

  mllp_sources = {
    adt = { port = 2575 }
  }
  probe_port = 9091

  egress_rules = {
    https = {
      port        = 443
      cidr_blocks = ["0.0.0.0/0"]
    }
    lab = {
      port        = 2576
      cidr_blocks = var.lab_cidr_blocks
    }
  }

  environment = {
    PATHWAYS_STORAGE = "postgres"
  }
  secrets = {
    PATHWAYS_KEY_2026_11 = var.master_key_secret_arn
  }

  database_backup_retention_days = var.backup_retention_days
}

# The key the replicated backups are encrypted under, in the backup region. It must outlive the
# primary region's key: a restore there never needs the first region.
resource "aws_kms_key" "backup" {
  provider = aws.backup

  description             = "Pathways backup: the database's automated backups replicated to ${var.backup_region}"
  enable_key_rotation     = true
  deletion_window_in_days = 30
}

resource "aws_kms_alias" "backup" {
  provider = aws.backup

  name          = "alias/pathways-backup-database"
  target_key_id = aws_kms_key.backup.key_id
}

resource "aws_db_instance_automated_backups_replication" "this" {
  provider = aws.backup

  source_db_instance_arn = module.pathways.database_instance_arn
  kms_key_id             = aws_kms_key.backup.arn
  retention_period       = var.backup_retention_days
}
```

### project/channels/adt-to-lab/channel.yaml

```yaml title="examples/cross-region-backup/project/channels/adt-to-lab/channel.yaml"
# One channel: take ADT over MLLP from the hospital system and send each admission on to the lab's
# MLLP receiver. The lab's address is a placeholder.
name: adt-to-lab
format: hl7v2

source:
  mllp:
    # mllp_sources.adt in the example's main.tf: the network load balancer passes this port through.
    port: 2575
    host: 0.0.0.0
    # The engine terminates TLS itself. Add the certificate and key to the image.
    tls:
      cert: ../../certs/server.pem
      key: ../../certs/server.key

transform: ./transform.ts

destinations:
  - mllp:
      # egress_rules.lab in the example's main.tf lets the engine reach this port.
      host: lab.example.com
      port: 2576
      tls:
        ca: ../../certs/lab-ca.pem
```

### project/channels/adt-to-lab/transform.ts

```ts title="examples/cross-region-backup/project/channels/adt-to-lab/transform.ts"
// Only admissions go to the lab, addressed to it in MSH-5. Every other message is filtered out.
import type { Transform } from "@cosyte/pathways";

export default ((msg) => {
  if (!msg.is("ADT^A01")) return null;
  msg.setField("MSH.5", "LAB");
  return msg;
}) satisfies Transform;
```

### project/pathways.yaml

```yaml title="examples/cross-region-backup/project/pathways.yaml"
# The Pathways project this example deploys: copy it into a project `pathways init` made, build the
# project's image (its Dockerfile names the Pathways image by digest) and pass that image's digest as
# the example's image variable. Every value the module sets reaches the engine as an environment
# variable this file reads with { env: NAME }.

storage:
  kind: { env: PATHWAYS_STORAGE, default: sqlite }
  postgres:
    # The module writes the database's URL to a secret ECS injects as PATHWAYS_DATABASE_URL.
    url: { env: PATHWAYS_DATABASE_URL }
    # The RDS global bundle, https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem, added
    # to the image: the database refuses connections without TLS.
    tls: { ca: certs/rds-global-bundle.pem }

encryption:
  # 32 random bytes in base64, in a Secrets Manager secret the example passes as secrets.
  keys: [{ id: "2026-11", env: PATHWAYS_KEY_2026_11 }]
  current: "2026-11"

# The load balancer checks /readyz here, and ECS runs `pathways probe` against /livez. host:
# 0.0.0.0 lets them reach it; it carries no message.
probes:
  port: 9091
  host: 0.0.0.0
  plaintext: true
```
