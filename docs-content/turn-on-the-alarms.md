# Turn on the alarms

The engine serves its metrics at `/metrics` on its health endpoint
([Collect metrics](https://docs.cosyte.com/pathways/collect-metrics)). With `alarms_enabled`, the
module runs an OpenTelemetry collector beside the engine in its task, sends four of those metrics to
CloudWatch, and creates four CloudWatch alarms that publish to an SNS topic you give. It is off by
default: until you turn it on, the module creates none of it and nothing of it bills.

## What you need first

- **An SNS topic**, and its subscriptions: the alarms publish to it when they go into alarm and when
  they come back to OK. If the topic is encrypted, its key policy must let CloudWatch use the key.
- **The collector's image, by digest.** AWS Distro for OpenTelemetry
  ([public.ecr.aws/aws-observability/aws-otel-collector](https://gallery.ecr.aws/aws-observability/aws-otel-collector))
  has every component the module's configuration uses: the `prometheus` receiver, the `filter` and
  `metricstransform` processors and the `awsemf` exporter. Pick a version and pin it by the digest
  the registry gives for it; the module refuses a tag alone. If you copy it to your own ECR
  repository, the execution role may pull from that repository and no other.
- **A health endpoint** in your `pathways.yaml`, on `alarms_health_port` (9090 by default):

  ```yaml title="pathways.yaml"
  health:
    port: 9090
    plaintext: true
  ```

  With no `host` it binds to 127.0.0.1, so only the collector in the same task reaches it, over
  plain HTTP that never leaves the task. With no `auth` it asks for the bearer token in
  `PATHWAYS_HEALTH_TOKEN`, which the module sets. The port is not mapped and no security group rule
  opens it.

## Turn it on

```hcl title="main.tf"
module "pathways" {
  source = "github.com/cosyte/terraform-aws-pathways?ref=<commit or tag>"
  # ...the inputs you already set

  alarms_enabled         = true
  alarms_sns_topic_arn   = "arn:aws:sns:us-east-1:123456789012:pathways-alarms"
  alarms_collector_image = "public.ecr.aws/aws-observability/aws-otel-collector:<version>@sha256:<digest>"
}
```

The apply creates the token's secret, the metrics log group, the task role's policy on it and the
four alarms, and gives the service a new task definition revision with the collector in it, so ECS
replaces the engine. [`examples/alarms`](./example-alarms.md) is a whole deployment with them on.

## What it creates

- **A health token**, generated by the module and written to a Secrets Manager secret,
  `pathways/<name>/health-token`, encrypted under the module's key. It is generated by an ephemeral
  resource and written in a write-only argument, so neither the plan nor the state holds it, and no
  output gives it: `health_token_secret_arn` names the secret. ECS injects it into the engine as
  `PATHWAYS_HEALTH_TOKEN` and into the collector, not into the migrate task. To change it, raise
  `alarms_health_token_version` by one, apply, and force a new deployment of the service, since
  both containers read it when a task starts.
- **The collector**, a second container in the engine's task, not essential, so the engine runs on
  if it stops. Every 30 seconds it reads `http://127.0.0.1:<alarms_health_port>/metrics` with the
  token, keeps `pathways_store_up`, `pathways_oldest_pending_age_seconds`,
  `pathways_messages_refused_total` and, of `pathways_settled_destinations_total`, only the outcome
  `failed`, and drops every other metric. It folds away every channel, destination and outcome
  label (the minimum for store up, the maximum for the oldest pending age, the sum for the two
  counters), so no channel or destination name leaves the task, and labels each with the one
  dimension `Deployment = <name>`. It logs to the engine's log group under the stream prefix
  `metrics-collector`.
- **The metrics log group**, `/pathways/<name>/metrics`, encrypted under the module's key and kept
  for `log_retention_days`. The collector writes the four metrics there as CloudWatch embedded
  metric format lines, and CloudWatch turns them into metrics in the `Pathways` namespace. The task
  role may create streams in it and write to it, and nothing else.
- **Four alarms**, each publishing to your topic on alarm and on OK:

| Alarm                                 | Fires when                                                                                       | Its input, and default                        |
| ------------------------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------- |
| `pathways-<name>-store-down`          | `pathways_store_up` is below 1, or missing, for that many minutes in a row                       | `alarms_store_down_minutes`, 2                |
| `pathways-<name>-oldest-pending-age`  | the oldest delivery waiting on any destination has waited longer than that for 5 minutes         | `alarms_oldest_pending_age_seconds`, 600      |
| `pathways-<name>-refused-messages`    | the sources refused more bodies than that in 15 minutes, all channels together                   | `alarms_refused_messages_threshold`, 0        |
| `pathways-<name>-settled-failed`      | more messages than that settled as failed with a destination in 15 minutes                      | `alarms_settled_failed_threshold`, 0          |

A missing minute counts for store down, so an engine or a collector that stopped reporting fires
it too. The engine leaves the oldest pending age out while it cannot read its database, which store
down already covers, so a missing minute does not count there.

## What it costs

We give what bills, not prices: AWS sets those per region and changes them. Price each line in the
[AWS Pricing Calculator](https://calculator.aws/) for your region, or on the
[CloudWatch](https://aws.amazon.com/cloudwatch/pricing/),
[Secrets Manager](https://aws.amazon.com/secrets-manager/pricing/) and
[Fargate](https://aws.amazon.com/fargate/pricing/) pricing pages.

| What | How it bills while it runs |
| --- | --- |
| Four custom metrics, one dimension each | per metric per month, the same whatever the number of channels and destinations |
| Four standard resolution alarms | per alarm metric per month |
| The collector's lines in CloudWatch Logs | per GB ingested, and per GB-month kept for `log_retention_days` |
| The token's secret | per secret per month, and per 10,000 calls (ECS reads it when a task starts) |
| The collector's share of the task | inside the task's `cpu` and `memory`, which Fargate bills per second; raise them if the engine needs all it has |
| SNS | per notification your topic delivers, as your subscriptions bill |

Keeping the channel and destination labels would make one metric per channel or destination and
outcome, and the bill grow with each; the module folds them away for that reason. The engine's
`/metrics` and its own docs keep every label, for a collector of your own.

## Turn it off

Set `alarms_enabled = false` and apply. The alarms, the metrics log group with its lines, the task
role's policy and the token's secret are deleted (the secret after Secrets Manager's 7 day recovery
window), and the engine's task goes back to the engine alone. Take the `health:` block out of your
`pathways.yaml` too, or give it a token of your own: without `PATHWAYS_HEALTH_TOKEN` the engine
does not start.
