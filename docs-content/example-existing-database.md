# The existing-database example

`examples/existing-database` runs the engine on a PostgreSQL database you already run, through two
inputs: `database_url_secret_arn` and `database_security_group_id`.

## What it deploys

In an existing VPC, beside your database:

- **One engine** on ECS Fargate, 1 vCPU and 2 GiB, and the migrate task definition, which migrates
  your database's schema when your CI runs it.
- **No database.** The module creates no RDS instance, no subnet group, no parameter group and no URL
  secret. ECS injects your secret as `PATHWAYS_DATABASE_URL`.
- **Two security group rules**: the engine may reach your database's group on 5432, and your
  database's group admits the engine on 5432.
- **A network load balancer**, internal, with one MLLP listener, the KMS key for the logs, the log
  groups, the engine's security groups and the roles.
- **The channel** in `project/`: ADT over MLLP in, admissions over MLLP out to the lab.

## What your database needs

- A database and a user that are Pathways' alone, reachable from the engine's subnets on 5432.
- TLS, with the server's certificate authority in `tls.ca` of `pathways.yaml`.
- A Secrets Manager secret holding one `postgres://` URL with the user and password. If a customer
  managed key encrypts it, list the key in `secrets_kms_key_arns`.

## When to choose it

When a database team already runs PostgreSQL for you, or when you restore a backup into a new
instance, as [cross-region-backup](./example-cross-region-backup.md) describes, and point a
deployment at it.

## What it does not cover

- The database's backups, encryption, failover, upgrades and password rotation, which are yours.
  After a rotation, update the secret and start a new deployment of the service.
- A port other than 5432, and a database in another VPC.

## What it costs to leave running

We give what bills, not prices: AWS sets those per region and changes them. Price each line in the
[AWS Pricing Calculator](https://calculator.aws/) for your region.

| What | How it bills while it runs |
| --- | --- |
| The engine, Fargate, 1 vCPU and 2 GiB | per second the task runs, all month |
| The network load balancer | per hour it exists, and per capacity unit used |
| The module's KMS key | per month, and per request |
| CloudWatch Logs | per GB ingested, and per GB-month kept for `log_retention_days` (365) |
| Your NAT gateway, already there | per GB the tasks send through it |
| Your database, already there | on your bill already; Pathways adds its storage, connections and load |

```md title="examples/existing-database/README.md"
# existing-database

Pathways on a PostgreSQL database you already run, instead of the RDS instance the module creates.

## What it builds

In an existing VPC, beside your database:

- one engine on ECS Fargate, 1 vCPU and 2 GiB, and the migrate task definition, which migrates your
  database's schema when your CI runs it;
- no database: with `database_url_secret_arn` the module creates no RDS instance, no subnet group, no
  parameter group and no URL secret. ECS injects your secret as `PATHWAYS_DATABASE_URL`;
- two security group rules for `database_security_group_id`: the engine may reach your database's
  group on 5432, and your database's group admits the engine on 5432;
- an internal network load balancer with one MLLP listener, the KMS key (for the logs), the log
  groups, the engine's security groups and the roles;
- the one channel in [`project/`](project): ADT over MLLP in, admissions over MLLP out to the lab.

## When to choose it

When a database team already runs PostgreSQL for you, with its own backups, patching, monitoring
and failover, and Pathways should be one more database on it. Or when you restore a backup into a
new instance, as [`cross-region-backup`](../cross-region-backup) describes, and point a deployment
at it.

## What your database needs

- PostgreSQL that Pathways supports, reachable from the engine's subnets on 5432.
- A database and a user that are Pathways' alone: the migrate task creates and changes its tables.
- TLS. The engine verifies the server's certificate against `tls.ca` in `pathways.yaml`: for RDS or
  Aurora, the RDS global bundle. Set `rds.force_ssl` on the database's side.
- The secret: one `postgres://` URL with the user and password, in a Secrets Manager secret. If a
  customer managed key encrypts it, list that key in `database_url_secret_kms_key_arns`.

## What it costs

We give what bills, not prices: AWS sets those per region and changes them.

- Fargate, per second, for 1 vCPU and 2 GiB, all month.
- The network load balancer per hour and per capacity unit.
- The module's KMS key, and CloudWatch Logs per GB ingested and stored.
- Your NAT gateway, per GB the tasks send through it.
- The database is on your own bill already. Pathways adds its storage, and its connections and load.

## What it does not cover

- The database itself: its backups, its encryption, its failover, its version upgrades and its
  password rotation are yours. After you rotate the password, update the secret and restart the
  engine (a new deployment of the service) so it reads the new URL.
- A port other than 5432: the module's rules are on 5432.
- A database in another VPC: the two rules name security groups, which works within one VPC (and
  across a peering in the same region). We have not tested other routes to a database.
- The other `database_` inputs (`database_instance_class` and the rest) do nothing with an existing
  database.

## Use it

Every value in [`variables.tf`](variables.tf) is a placeholder. Create the database and user, store
the URL in a secret, copy `project/` into a project `pathways init` made, add the CA bundle for your
database, the MLLP source's certificate and key and the lab's CA under `certs/`, build the image and
push it, set the variables, then plan and apply from your own pipeline with your own credentials. CI
here validates this directory and tests it against mocked providers
(`tests/example-existing-database`); nothing in this repository applies it.
```

### main.tf

```hcl title="examples/existing-database/main.tf"
# Pathways on a PostgreSQL database you already run, instead of the RDS instance the module creates:
# an RDS or Aurora PostgreSQL instance your database team keeps, in the same VPC. The module creates
# no database, no subnet group and no URL secret. The engine reads its connection URL from your
# secret (database_url_secret_arn), and the module lets the engine reach your database's security
# group on 5432 and adds a rule to that group admitting the engine (database_security_group_id).
#
# Every value here is a placeholder: the VPC, subnet and security group ids, the account id
# 123456789012, the image digest and the secret ARNs. Put your own in before you plan.

provider "aws" {
  region = var.region

  default_tags {
    tags = {
      Project = "pathways-existing-database"
    }
  }
}

module "pathways" {
  source = "../.."

  name   = "existing-db"
  vpc_id = var.vpc_id

  private_subnet_ids  = var.private_subnet_ids
  allowed_cidr_blocks = var.allowed_cidr_blocks

  image = var.image

  mllp_sources = {
    adt = { port = 2575 }
  }
  probe_port = 9091

  egress_rules = {
    https = {
      port        = 443
      cidr_blocks = ["0.0.0.0/0"]
    }
    lab = {
      port        = 2576
      cidr_blocks = var.lab_cidr_blocks
    }
  }

  environment = {
    PATHWAYS_STORAGE = "postgres"
  }
  secrets = {
    PATHWAYS_KEY_2026_11 = var.master_key_secret_arn
  }

  # Your database. The secret holds one postgres:// URL with its user and password, and ECS injects
  # it as PATHWAYS_DATABASE_URL. If it is encrypted under a customer managed key, add that key to
  # secrets_kms_key_arns so the task execution role may read it.
  database_url_secret_arn    = var.database_url_secret_arn
  database_security_group_id = var.database_security_group_id
  secrets_kms_key_arns       = var.database_url_secret_kms_key_arns
}
```

### project/channels/adt-to-lab/channel.yaml

```yaml title="examples/existing-database/project/channels/adt-to-lab/channel.yaml"
# One channel: take ADT over MLLP from the hospital system and send each admission on to the lab's
# MLLP receiver. The lab's address is a placeholder.
name: adt-to-lab
format: hl7v2

source:
  mllp:
    # mllp_sources.adt in the example's main.tf: the network load balancer passes this port through.
    port: 2575
    host: 0.0.0.0
    # The engine terminates TLS itself. Add the certificate and key to the image.
    tls:
      cert: ../../certs/server.pem
      key: ../../certs/server.key

transform: ./transform.ts

destinations:
  - mllp:
      # egress_rules.lab in the example's main.tf lets the engine reach this port.
      host: lab.example.com
      port: 2576
      tls:
        ca: ../../certs/lab-ca.pem
```

### project/channels/adt-to-lab/transform.ts

```ts title="examples/existing-database/project/channels/adt-to-lab/transform.ts"
// Only admissions go to the lab, addressed to it in MSH-5. Every other message is filtered out.
import type { Transform } from "@cosyte/pathways";

export default ((msg) => {
  if (!msg.is("ADT^A01")) return null;
  msg.setField("MSH.5", "LAB");
  return msg;
}) satisfies Transform;
```

### project/pathways.yaml

```yaml title="examples/existing-database/project/pathways.yaml"
# The Pathways project this example deploys: copy it into a project `pathways init` made, build the
# project's image (its Dockerfile names the Pathways image by digest) and pass that image's digest as
# the example's image variable. Every value the module sets reaches the engine as an environment
# variable this file reads with { env: NAME }.

storage:
  kind: { env: PATHWAYS_STORAGE, default: sqlite }
  postgres:
    # The module writes the database's URL to a secret ECS injects as PATHWAYS_DATABASE_URL.
    url: { env: PATHWAYS_DATABASE_URL }
    # The RDS global bundle, https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem, added
    # to the image: the database refuses connections without TLS.
    tls: { ca: certs/rds-global-bundle.pem }

encryption:
  # 32 random bytes in base64, in a Secrets Manager secret the example passes as secrets.
  keys: [{ id: "2026-11", env: PATHWAYS_KEY_2026_11 }]
  current: "2026-11"

# The load balancer checks /readyz here, and ECS runs `pathways probe` against /livez. host:
# 0.0.0.0 lets them reach it; it carries no message.
probes:
  port: 9091
  host: 0.0.0.0
  plaintext: true
```

```hcl title="examples/existing-database/variables.tf"
  description = "The Secrets Manager secret holding the master key: 32 random bytes in base64."

  description = "The Secrets Manager secret holding your database's connection URL, postgres://<user>:<password>@<host>:5432/<database>, for a database and a user that are Pathways' alone."
```
